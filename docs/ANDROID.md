# Android — runtime, editor and build

Lumen2D's Android story has two halves: `engine-android` (the engine's backends, usable by any app)
and `app-android` (Lumen2D Studio, the editor). Both are plain Kotlin against the Android framework
— the engine module deliberately has **no AndroidX dependency**, which keeps it small, keeps it
compatible from API 24 up, and means a game built on it can ship without an AndroidX runtime.

---

## 1. Modules and requirements

| | `engine-android` | `app-android` |
| --- | --- | --- |
| Type | `com.android.library` | `com.android.application` |
| Namespace | `dev.lumen2d.android` | `dev.lumen2d.studio` |
| Dependencies | `engine-core`, Kotlin stdlib | `engine-core`, `engine-android`, `androidx.core` (FileProvider only) |
| compileSdk / targetSdk | 36 | 36 |
| minSdk | 24 (Android 7.0) | 24 |
| Kotlin / AGP | 2.4.20 / 8.13.0 | 2.4.20 / 8.13.0 |
| Output | `engine-android-*.aar` | `app-android-debug.apk` / `app-android-release.apk` (CI artifact `lumen2d-studio-apk`) |

The app's release build enables R8 (`proguard-rules.pro`) and resource shrinking; the rules keep the
two activities, the `dev.lumen2d.android.**` entry points, the framework-inflated view constructors
and enum `values()`/`valueOf()` (scene and input-map JSON is parsed by name), and nothing else — the
engine is reflection-free by design, so shrinking cannot break gameplay code.

## 2. What `engine-android` provides

| Class | Role |
| --- | --- |
| `AndroidPlatform` | `Platform` implementation: `lib://` over the APK assets, `user://` under `filesDir/lumen/user`, settings via `SharedPreferences`-free `JsonSettingsStore`, device services (vibration, clipboard, density, orientation, share, toast, locale), `AndroidAudioOutput` created eagerly, SAF file picker |
| `AssetFileSystem` | read-only `VirtualFileSystem` over `AssetManager`; the file tree is walked once and cached (asset listing is recursive and slow), and directories are synthesised from the cached paths |
| `AndroidAudioOutput` | streams the mixer's 16-bit PCM into an `AudioTrack` (streaming mode, non-blocking writes, silent fallback if the device refuses to open one) |
| `LumenGameView` | the game surface: a `View` driven by `Choreographer` (vsync cadence, no thread, no wake lock), software renderer scaled into the view, touch → design coordinates (`toDesign`, `worldToView`, `designToWorld`), an **editor hook** the Studio drives (`onDesignTouch(design, phase)`, `onDesignTap`, `selection`, `overlay`) with `nodeSize`/`pickNodeAt` hit-testing |
| `LumenAndroid` | facade: `platform(context)`, `openProject`, `openGame`, `createProject`, `play(view, …)`, `library(platform)` (the asset library + provenance), `projectsDirectory`, `savesDirectory` |
| `ProjectStore` | lists projects as `ProjectEntry` (title, slug, config, counts, modified time) and creates/renames/duplicates/deletes them |
| `ProjectArchive` | `.lumenzip` export/import (ZIP of the project folder, skipping builds and caches) with pack-id detection |
| `SampleInstaller` | copies the APK's sample games into app storage on first launch, and can install a library pack into writable storage for editing |
| `AndroidFilePicker` | `ActivityResult`-free SAF picker (`ACTION_OPEN_DOCUMENT`) with MIME filters, cache copy and deliver step, used by the hub's import button |

## 3. What `app-android` provides

* `MainActivity` — the project hub (see [EDITOR.md](EDITOR.md#1-the-hub-mainactivity)).
* `StudioActivity` — the five-panel editor over a live engine viewport.
* `StudioSession` — the editing model: open scene, selection, undo/redo command stack, add/delete/
  duplicate/rename/move nodes, property edits, save, reload scripts.
* `SceneTreeView`, `InspectorView`, `AssetBrowserView`, `ScriptEditorPanel`, `ConsolePanel` — the
  panels; `StudioTheme.kt` holds the palette and the widget helpers (`dp`, `label`, `button`,
  `pill`, `sliderRow`, `scrolling`, `roundedBackground`, …) the whole UI is built from.
* `ProjectSharing` — `FileProvider` wrapper so exported `.lumenzip` archives can leave the app
  (`applicationId.fileprovider`, paths declared in `res/xml/file_paths.xml`).
* `AndroidManifest.xml`, `res/values/{strings,colors,themes}.xml`, five `mipmap-*` launcher icons
  (generated by `tools/make-android-icons.py`) and `proguard-rules.pro`.

The editor uses framework views on purpose: no Compose, no Material, no themes beyond a dark
`Theme.Material.NoActionBar`. The UI is ~2 200 lines of Kotlin and every widget is inspectable —
and the engine's own drawing code stays the only renderer in the app.

## 4. What the APK contains

```
assets/packs/base/**         lib://packs/base      the generated asset library (17 assets, CC0)
assets/packs/kenney/**       lib://packs/kenney    imported Kenney kit (CC0, 180 tiles)
assets/sources/**            lib://sources         provenance index shown in the asset browser
assets/samples/**            bundledSamples        the three sample games, seeded on first launch
```

`gradle :app-android:assembleDebug` first runs `:engine-desktop:exportContent` (which regenerates
the library and the samples from the engine) and stages the result into the APK's assets. Content is
therefore never stale relative to the code: a build that would produce different art fails while
regenerating it, not on a user's device.

Content types that matter for startup (`wav`, `png`, `json`, `lumen`, `tmx`, `tsx`, `fnt`) are listed
in `androidResources.noCompress`, so the runtime reads them without a decompression pass.

## 5. Building

```bash
# with an Android SDK + JDK 17
gradle :engine-android:assembleDebug      # the engine library
gradle :app-android:assembleDebug         # the editor APK
gradle :app-android:assembleRelease       # R8 + resource shrinking (signed with the CI keystore)
```

Release signing uses a keystore from `$LUMEN_KEYSTORE` when one is provided (CI creates the standard
debug keystore), and falls back to AGP's own debug signing config otherwise — so a clean checkout
always builds an installable release APK.

### CI

`.github/workflows/android.yml` runs on pushes to `main`/`arena/*`, on tags and on pull requests, and
does not simply build the APK — it verifies it:

1. **Engine core tests** — JDK 17, Gradle 8.14.3, `:engine-core:engineTests` (125 tests).
2. **Asset library, samples and previews** — regenerates the content and fails if the committed
   files differ from the engine's output, smoke-checks every sample headlessly, renders the seven
   preview screenshots, and self-tests the APK verifier.
3. **Build and verify the Android APK** — installs `platforms;android-36` + `build-tools;36.0.0`
   into the runner's SDK, assembles debug + release, and verifies both with `tools/verify-apk.sh`
   (manifest, signature, dex, pack manifests, sidecars, provenance index, sample projects,
   `noCompress`, and an exact comparison against the repository's content).
4. **Install and run the APK on an emulator** — boots a headless API 30 emulator, installs the debug
   APK, checks that the hub starts and lists all three bundled sample games (which proves the
   packaged `assets/samples` were read and seeded on device), taps **Play**, and requires a
   `Scene … loaded` line from the engine in logcat. Screenshots of the hub and the running editor are
   uploaded as `lumen2d-device-screenshots`.
5. **Re-verify the artifacts and publish the release** — downloads the uploaded APKs, verifies them a
   second time independently, and refreshes the **latest-build** release (or the tag release) with
   the APKs, their SHA-256 checksums, both verification reports and the on-device report in the
   release notes, plus the emulator screenshots as `device-hub.png` / `device-editor.png` assets.

The APK is therefore only published after it has been inspected statically *and* executed on a
device. `docs/BUILDING.md` §6 documents the individual checks and how to run them locally.

### Working without an Android SDK

The sandbox that developed this repository had no Android SDK, so the Android code is verified
offline instead:

```bash
tools/typecheck-android.sh engine    # engine-android only
tools/typecheck-android.sh app       # app + generated R stub
tools/typecheck-android.sh all       # both (default)
```

`tools/android-stubs/src/*.kt` are hand-written declarations of the framework APIs the engine uses
(and `tools/android-stubs/src/androidx_core.kt` for `FileProvider`). They are **type-check only** —
never compiled into anything, never shipped — and `kotlinc` is run against them exactly like it is
run against the real `android.jar`. `tools/generate-r-stub.py` turns `app-android/src/main/res` into
an `R` class in `out/` (never in `src/`, where it would collide with AGP's own generated class).
Together they catch typos, renamed members and signature mistakes long before a device or an SDK is
involved; the APK itself is still produced by Gradle + the SDK in CI.

## 6. Runtime notes and limits

* **Frame loop** — `LumenGameView` ticks on `Choreographer` vsync and renders into a scaled
  `Bitmap`/`Canvas`; `Game.attachRenderer` receives the software renderer, so the same draw calls
  produce the same pixels as on desktop.
* **Lifecycle** — the editor's `StudioActivity` pauses the engine in `onPause` and resumes in
  `onResume`; `LumenGameView.close()` releases the renderer, textures and audio.
* **Storage** — projects, saves and exports live under `filesDir/lumen`; exported archives are
  written to `getExternalFilesDir(null)/exports` when external storage is available, because the
  share sheet needs a real file.
* **Memory** — the software framebuffer at 480×270 with 3× upscale is ~0.5 MB per frame; textures
  decode on demand and are cached, so a sample game's working set stays a few megabytes.
* **No network** — the engine never touches the network: imported packs are vendored in the
  repository/APK, and everything else is local.
