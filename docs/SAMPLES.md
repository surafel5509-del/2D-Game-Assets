# Sample games

Three complete projects live in `sample-games/`. They are **generated by engine code**
(`engine-desktop`: `SampleGames.kt`) and **checked headlessly in CI**, so they cannot drift away from
the engine: if a node API, a script builtin or an asset reference changes, the sample build or the
smoke check fails.

Play any of them with the desktop CLI:

```bash
CP="out/classes/core:out/classes/desktop:$HOME/.cache/tools/kotlin/lib/kotlin-stdlib.jar"
CLI="java -cp $CP dev.lumen2d.desktop.LumenDesktopKt"

$CLI --game sample-games/hello-lumen2d
$CLI --game sample-games/pixel-platformer
$CLI --game sample-games/neon-shooter
```

Or open them on Android: they are seeded into app storage on first launch, so **Play** in the hub
runs them immediately. All three use only CC0 content from the bundled library.

---

## `hello-lumen2d` — the smallest complete game

The starting point for reading the engine: a tilemap floor, an animated character, a camera that
follows it and a script that drives it from the input map.

| File | What it is |
| --- | --- |
| `scripts/player.lumen` | movement, gravity and jumping (about 30 lines) |
| `scenes/main.scene.json` | the level: tilemap, player, sprite, camera, background |
| `project.lumen` | 480×270, gravity, audio buses, `assetPacks: ["lib://packs/base"]` |
| `input_map.json` | keyboard bindings plus virtual buttons for touch |

Verified by `--check`: 13 nodes, 3 bodies, 3 textures — a small project that still exercises the
scene graph, tilemap rendering, physics, animation, assets and scripting.

Read it first if you want to learn the engine, then copy it (`lumen2d --new "My Game"`) and start
changing things.

## `pixel-platformer` — a complete platformer

A real game in one script and two scenes: pits, one-way platforms and spikes in a 60×18 tilemap,
nine coins, a patrolling slime, a goal flag, a HUD with a coin counter and a health bar, a title
screen, sound effects, camera shake and a restart flow.

| File | What it is |
| --- | --- |
| `scenes/menu.scene.json` | title screen (the project's start scene) |
| `scenes/level_1.scene.json` | the level (30 nodes: tilemap, player, 9 coins, slime, flag, HUD, camera) |
| `scripts/menu.lumen` | any accept/fire/jump press starts the level |
| `scripts/game.lumen` | movement with coyote time and jump buffering, coin pickups, slime patrol, damage, HUD updates, level clear |
| `input_map.json` | A/D or ←/→, Space/Z to jump, Esc to pause, plus touch buttons |

**Controls:** **A/D** or **←/→** move, **Space/Z** jump, **Esc** pause. On a phone the same project
shows its touch buttons — the scene contains both, and the scripts never branch on the platform.

Things to look at in `scripts/game.lumen`: coyote time (`coyote`), input buffering (`jump_buffer`),
invulnerability after damage (`invulnerable`), particle feedback (`Dust` + `set_timer`), HUD access
by node path (`UI/HUD/CoinBar.set_count(...)`) and the win condition. Headless check: 30 nodes,
124 draw calls, 118 sprites, 20 550 drawn pixels, 3 physics bodies, 24 assets, 8 textures.

## `neon-shooter` — prefabs, waves and scoring

A vertical shooter that demonstrates the gameplay nodes rather than raw drawing: prefab instancing
(`spawn` / `instantiate`), wave spawning on a timer, enemy and bullet prefabs, particle hits, a score
HUD, and a restart flow.

| File | What it is |
| --- | --- |
| `scenes/space.scene.json` | the playable scene (starfield, player, HUD, spawner) |
| `scenes/prefabs/bullet.scene.json` | bullet prefab, instanced by the script |
| `scenes/prefabs/enemy.scene.json` | enemy prefab, chosen per wave |
| `scripts/game.lumen` | firing, waves, collisions, score, restart |

**Controls:** **←/→** or **A/D** steer, **Space/X** fires; **Space** restarts after a game over.
Headless check: 16 nodes, 6 textures, 1 body (the player), 14 draw calls that vary with the wave.

## How they are generated

`SampleGames` builds each project with the same APIs a game would use:

```kotlin
SampleGames(target).buildAll()      // writes all three into `sample-games/`
```

Each project is created with `Project.create`, given a `GameConfig` (title, package id,
`assetPacks = ["lib://packs/base"]`), the standard input map (`DefaultInputMap.bindings()`), then
scenes built from nodes — tilemaps via `TileMapData.ensureLayer(...)` / `TileMapNode.setTile(...)`,
bodies as `CharacterBody2DNode` + `CollisionShape2DNode` children, UI through `CanvasLayer` +
`HudBarControl`/`ProgressBarControl`/`TouchButtonControl` — and scripts written as `.lumen` sources.
Scenes are saved as JSON, so the result is exactly what the editor would have produced.

The generator deletes the scaffolding scene `Project.create` seeds (`scenes/main.scene.json`) when a
game supplies its own, and CI runs `:engine-desktop:exportContent` before the APK build, so the
shipped content is always a fresh product of the current engine.

## Extending a sample

1. Copy it: `cp -r sample-games/pixel-platformer ~/my-game` (or open it in Studio and use **Export**).
2. Play it: `$CLI --game ~/my-game`.
3. Edit scenes in the Android editor or by hand — the JSON is documented in
   [ASSETS.md](ASSETS.md#1-mounts-and-ids) and [ENGINE.md](ENGINE.md#3-scene-graph).
4. Add art from the library (`lib://packs/base/...`, `lib://packs/kenney/...`) or your own pack
   (see [ASSETS.md](ASSETS.md#8-adding-your-own-pack)).
5. Keep `--check` passing while you go: it catches broken script paths, missing assets and scenes
   that no longer load long before you open the game.
